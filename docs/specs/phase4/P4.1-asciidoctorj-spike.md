# P4.1 Spike: AsciidoctorJ from the AsciiDoc plugin

Plan: [PHASE4.md](../../PHASE4.md). Decisions under test: [ADR 0002](../../adr/0002-asciidoc-parser.md),
[ADR 0003](../../adr/0003-asciidoctorj-from-asciidoc-plugin.md), [ADR 0005](../../adr/0005-asciidoc-block-model.md).

## Goal

Find out, before any production code, whether Markdown Review can load and run AsciidoctorJ from the JetBrains
AsciiDoc plugin, how fast it is, and how precise its source map is. The result is a yes or no on ADR 0003 and a
list of the line-mapping fallbacks ADR 0005 needs.

## Scope

On a throwaway branch, not merged:

1. `markdown-review-withAsciiDoc.xml` and `<depends optional="true">` on `org.asciidoctor.intellij.asciidoc`; the
   AsciiDoc plugin as an IntelliJ Platform plugin dependency in Gradle for IC 2025.1.3, AsciidoctorJ `compileOnly`.
2. An internal action, "Dump AsciiDoc Blocks", in the optional descriptor. It creates an `Asciidoctor` instance with
   the AsciiDoc plugin's class loader as the thread's context class loader, calls `load` with `sourcemap: true` and
   `safe: SECURE` on the current editor's text, and writes the tree to the log: context, style, level, source line,
   and the converted title or text of each node.
3. Measurements on the fixture `20-large-file` converted to AsciiDoc, and on 1,000- and 10,000-line samples:
   - time and heap of the first `Asciidoctor.Factory.create()` and the first `load`;
   - steady-state `load` time per size (median of 10);
   - steady-state time to convert all inline content of the document (`getContent()` / `getText()` on every node).
4. Concurrency: two threads loading different documents on one instance, 1,000 times; any exception or wrong tree
   means calls must be serialized.
5. Source map checks on a sample that has: sections at every level, a preamble, paragraphs, admonition paragraphs and
   blocks, nested example/sidebar/quote blocks, lists with continuations and nested lists, checklists, description
   lists, callout lists, a table with one-line rows, multi-line rows and `a|` cells, listing and literal blocks with
   `[source,java]` and `[[anchor]]` lines, block titles, `ifdef` / `endif`, an `include::` line, line and block comments,
   and attribute entries in the header and body. For each node: is `getSourceLocation()` present, is the line right?
6. Unloading: disable and re-enable the AsciiDoc plugin while an instance exists; check that ours is released (no
   class loader leak reported by the platform's dynamic plugin checks).
7. `verifyPlugin` on every IDE in `pluginVerification`, with the dependency: no new problems at the configured
   failure levels.
8. Record the AsciidoctorJ version shipped by the AsciiDoc plugin for each IDE version in the verification list.

## Out of scope

Blocks, rendering, any change to the engine or the viewers.

## Results to record

- In ADR 0003: go or no-go, the class loader setup that works, the AsciidoctorJ versions, the unload behavior, and
  any `verifyPlugin` findings. On no-go, switch the ADR to the companion-plugin fallback and update PHASE4.md.
- In ADR 0005: which nodes lack a source location or have a wrong one, and which scanner fallbacks are needed.
- In ADR 0002: whether `load` is thread-safe on one instance.
- In PHASE4.md, NFR-12: the measured first-render and steady-state times, and whether the budget holds.

## Done when

- ADR 0002, 0003 and 0005 have their status changed to accepted (or revised and accepted), with the numbers above.
- The spike branch is deleted, or kept only as a reference linked from ADR 0003.
